# RabbitMQ TLS for Xray

This example enables TLS on the bundled RabbitMQ instance that Xray uses for messaging. RabbitMQ is shared between the `global` block (read by Xray) and the `rabbitmq` subchart's own block (read by the RabbitMQ pod itself) — both must be kept in sync.

See the [rabbitmq-tls-values.yaml](rabbitmq-tls-values.yaml) for the configuration example.

## How it works

- `global.rabbitmq.auth.tls.enabled` and `rabbitmq.auth.tls.enabled` must be set to the same value — the `global` copy is what Xray uses to decide whether to connect over TLS, and the `rabbitmq` copy is what the RabbitMQ subchart uses to decide whether to terminate TLS at all.
- The auto-generate-vs-bring-your-own toggle is `autoGenerated` (camelCase). This is easy to get wrong — some older guidance and third-party notes use the lowercase form `autogenerated`, which is not a real key and is silently ignored by the chart, leaving TLS certs unconfigured.
- Leaving `autoGenerated: true` (the default when TLS is enabled) has RabbitMQ generate its own self-signed certificate. To bring your own certificate instead, set `autoGenerated: false` and provide `existingSecret` under `rabbitmq.auth.tls` (and mirror the reference under `global.rabbitmq.auth.tls.existingSecret`).

## Deploy

```console
export MASTER_KEY=$(openssl rand -hex 32)
export JOIN_KEY=$(openssl rand -hex 32)
helm upgrade --install jfrog-platform --namespace jfrog-platform --create-namespace jfrog/jfrog-platform -f rabbitmq-tls-values.yaml \
  --set global.masterKey=$MASTER_KEY --set global.joinKey=$JOIN_KEY
```

## Notes

- This RabbitMQ instance is used by Xray only. If Xray is disabled (`xray.enabled: false`), also set `rabbitmq.enabled: false` to skip deploying it.
